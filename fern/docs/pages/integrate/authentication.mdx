Every API request is made on behalf of one account, and an **API key** is how a server proves it's allowed to act for that account. A key is not a user: it never logs in, it has no password, and it can be limited to exactly the operations and source addresses an integration needs. Treat it like a database credential — it can place calls that cost money.

## How keys work

- A key belongs to **one account**. You never send an account ID; everything the key does is scoped automatically. An organization with several accounts needs a key per account.
- It's sent as a Bearer token: `Authorization: Bearer tif_live_…`.
- The full key is shown **once**, at creation. Afterwards only its prefix (`tif_live_aBc…hijk`) is visible, for identification.
- It carries **scopes** — which resources it may read or write — and optionally an **IP allowlist** and an **expiry**.
- It acts as the **person who created it**, and never with more than that person's current role in the account allows. If their role is lowered or they leave the account, the key loses what the role no longer covers. Create integration keys as someone whose role will stay.

```bash title="First request"
curl "https://api.talkif.ai/api/v1/calls?status=inprogress" \
  -H "Authorization: Bearer $TALKIF_API_KEY"
```

## What a key can reach

A key reaches exactly the operations in the [API Reference](/api-reference), plus the [MCP server](/integrate/mcp) that exposes the same operations as tools (and, with the `session_bridge` scope, the experimental Connectors). Everything else in the dashboard — managing API keys, members and invitations, payment methods, your own profile and sign-in methods — needs a person signed in, and answers a key with `403 api_key_not_allowed`.

## Creating a key

In an organization account, Owners and Admins create and revoke keys — see [Members and roles](/account/members-and-roles).

<Steps>
  <Step title="Developer → Credentials → Create API Key">
    Name it for the system that will hold it ("CRM callback service", "Nightly campaign loader") — the name is how you'll recognise it in usage logs a year from now.
  </Step>
  <Step title="Choose scopes">
    The form starts on **Full access**. Narrow it: an integration that only places calls and reads results needs `calls:*` and `contacts:read`, not `billing` or `flows`. A key needs at least one scope; the form won't create a key without one.
  </Step>
  <Step title="Optionally restrict and expire">
    An **IP allowlist** (CIDRs) rejects requests from anywhere else with `403`. An **expiry** turns the key off on a date — right for a contractor's key or a migration window.
  </Step>
  <Step title="Copy the key now">
    Store it in your secret manager. It won't be shown again; if it's lost, create a new one and revoke the old.
  </Step>
</Steps>

## Scopes

A scope is `resource:action`. Actions are `read` (`GET` requests), `write` (every other method — so checking numbers with `POST /dnc/check` needs `dnc:write`), or `*` for both; `*` alone is **Full access** — every resource except Connectors.

| Resource | Covers |
|---|---|
| `calls` | Placing and ending calls, browser calls, history, transcripts, recordings, analysis, the real-time event stream |
| `flows` | Flows, versions, publish, validate, duplicate, status, tags |
| `flow_functions` | The account's reusable flow functions |
| `flow_templates` | Account templates, creating a flow from a template, saving a flow as a template |
| `contacts` | Contacts, import and export, tags |
| `phones` | Phone numbers and providers, buying and releasing numbers |
| `billing` | Balance, charges, costs, invoices, transactions (read-only by nature) |
| `analytics` | Flow and campaign analytics |
| `schedules` | Schedules **and campaigns**, with the campaigns' contacts |
| `dnc` | The Do Not Call list |
| `models` | The model and voice catalogue |
| `transfers` | Transfer destinations and groups, member tags and hours |
| `transfer_offers` | Viewing, accepting and declining transfer offers sent to [your app](/build/receive-transfers-in-your-app) — give the server that receives the webhooks only `transfer_offers:*` |
| `session_bridge` | **Connectors** (experimental): lets your own agents and coding sessions answer your voice agents. Not part of Full access — tick it by name |

<Note>
  The scope picker also lists `campaigns`, `templates` and `variables`. No API endpoint checks them today: campaign endpoints check `schedules`, and prompt templates and variables are dashboard-only. Grant `schedules` to a key that runs campaigns.
</Note>

A request outside the key's scopes fails with `403 api_key_insufficient_scope`. Examples: `["calls:*", "contacts:read"]`; `["schedules:*", "contacts:*"]` for a campaign loader (campaigns skip Do Not Call numbers on their own); `["billing:read"]` for a finance dashboard.

## When a key is refused

Every refusal says why in its `code`, so an integration can tell a revoked key from a missing scope:

| Status | `code` | Why |
|---|---|---|
| `401` | `api_key_invalid` | The key isn't recognised — mistyped, cut off when copied, or deleted |
| `401` | `api_key_revoked` | The key was revoked |
| `401` | `api_key_expired` | The key is past its expiry date |
| `403` | `api_key_ip_restricted` | The request came from an address outside the key's IP allowlist |
| `403` | `api_key_insufficient_scope` | The key's scopes don't cover this endpoint |
| `403` | `api_key_not_allowed` | The endpoint isn't open to API keys — it isn't part of the [API Reference](/api-reference) |
| `403` | `insufficient_permissions` | The current role of the person who created the key doesn't allow this |

The `401` codes mean the key itself won't work again: create a new one. The `403` codes are about this request: fix the scope, the allowlist or the endpoint and retry with the same key. All codes are on [Error codes](/api-reference/errors).

## Knowing what a key is doing

Each key keeps daily usage — request count, error count, approximate distinct source IPs — and its **50 most recent errors** with status, error code, path, method, request ID and time. Open the key under **Developer → Credentials** to see both. When an integration misbehaves, this is faster than your own logs: the request ID here matches the one in the API's error response.

## Rotation and revocation

You can change an active key's **scopes**, **name** and **IP allowlist** at any time under **Developer → Credentials → open the key**; the key value stays the same, so nothing needs redeploying. The expiry can't be changed — create a new key instead.

Revoking is immediate and permanent. To rotate without downtime:

1. Create the new key with the same scopes.
2. Deploy it to the integration.
3. Confirm the new key's usage counter is climbing and the old one's has stopped.
4. Revoke the old key.

Revoked and expired keys stay listed for audit; they can't be re-enabled.

## Limits

Up to **25 keys** per account; at least one scope per key; names 1–100 characters.

<Warning title="Never put an API key in a browser or mobile app">
  A key in client-side code is public. For browser voice calls use [Web calls](/sdks/browser) with a publishable key; for anything else, call Talkif from your own backend.
</Warning>

## Apps that sign in instead

An AI app that can't hold an API key — one that only takes a server URL — can ask a person to approve it instead, with **Sign in with Talkif** (OAuth 2.1). The app gets its own token for one account; the person sees and revokes it under **Developer → Integrations → Connected apps**. Such a token reaches Connectors only, not the API. See [MCP server](/integrate/mcp#sign-in-with-talkif).
